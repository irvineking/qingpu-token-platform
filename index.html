01 · 定位

定位与判断

平台做三件底座能力：统一调度网关、企业用量计量与结算、可解释的 AI 模型推荐分析。另有一件可叠加的落地功能：AI 企业化部署服务（按项目开通、独立核算）。另有两件可选项：政务级计量结算、补贴发放通道。

上游是各家已授权的模型原厂、推理托管与合规聚合渠道。下游首先是需要发票、预算、审计和责任主体的企业，尤其是国企与集团客户；若地方有算力或模型使用支持政策，再叠加选项，服务主管部门的额度核发与监管复盘。

判断一：壁垒不在接了多少模型

接模型是两周的活。真正留住客户的是计量准确率、对账差异率，以及预算、权限、审计、发票。这四样做不好，第二个月就会回到云厂商控制台或自己对接原厂。

判断二：国企买的是可追责，不是更便宜

公开报道已提示过灰产中转站风险。国企采购首先排除无授权、无对公、无专票的通道。政府背景支持让「正规通道 + 本地服务商」比纯低价中转更容易过会。

判断三：价差不能当主叙事

官方持续降价、云厂商集采会压缩渠道价差。平台要靠服务费、年框和自助化率活下来。财政补贴资金更不能算作平台流水。

判断四：政务能力按需开，不捆绑

没有可信账本就不能自动发补贴。没有书面政策和审核授权，就不应开通补贴通道。先把网关和出账做稳，再决定是否升级政务选项。

不做全网最低价，也不把「区级补贴平台」写成每家客户的默认形态。价格与授权市场对齐；政务选项只在有明确采购或政策需求时打开。
02 · 差异化

统一调度网关：政府支持与国企优势

统一调度网关是所有开通组合共用的第一入口。它被定义为国企可用的合规调度层：一次接入、多家授权模型、集团内多租户隔离，调用可回查、费用可分摊、数据出境属性可管控。

为什么国企需要独立调度层

  • 集团往往同时有客服、公文、知识库、安防智能化等多条业务线，模型需求不同，但不希望每个子公司单独签十几家厂商、对十几张账单。
  • 采购、信息化、保密办和业务部门的诉求不一致：业务要效果，财务要对公专票，合规要境内默认、日志留存、权限到人。
  • 直接用单一云厂商控制台会产生绑定顾虑；直接用市面中转，过不了合规审查。中间需要一个中立、可审计、有责任主体的调度入口。

我方相对纯技术中转 / 纯云厂商的优势

能力对国企意味着什么网关如何体现
政府背景支持沟通路径清楚，便于进入既有信息化与试点框架，降低「不知名中转」的一票否决对外以正规企业服务商身份提供调度，不包装成无主体的 API 店铺
对公与票据合同、专票、部门成本中心是采购刚需一个入口出账，按租户 / 项目 / Key 下钻，支持开票与回款核销
授权渠道避免号池、账号拆分、模型掺水等被公开提示过的风险只接入已签约的原厂、托管或合规聚合渠道；模型卡片标明来源与备案 / 出境属性
集团治理多法人、多预算科目、最小权限企业 / 部门 / 项目 / 成员四级隔离；Key 级模型白名单、额度和 IP 策略
本地交付系统要进现有 OA、安防、知识库，而不是只给一段 SDK网关保持 OpenAI 兼容，实施团队按项目对接，形成「调度 + 落地」闭环
可升级的政务账本后续若出现区级补贴或多部门监管，不必换平台同一套计量内核可升级为选项 A / B，而不是再造一套系统
说明：本文所称「政府背景支持」按内部既定合作与支持关系表述，不虚构具体主管单位、牌照或背书文件。区县级政策兑付仅作为开通组合示例。对外材料以法务审定的表述为准。

网关对国企客户的默认策略

境内优先

敏感数据租户默认只开放境内授权模型；境外模型不进入一期目录，也不进入可补贴白名单。

失败可切换、来源可证明

同模型至少准备两家授权渠道；健康探测后自动降权，账单可回查渠道而不是黑盒。

先预检再出站

余额、授信或补贴额度不足直接返回明确错误，避免请求打到上游后产生无法解释的成本。

03 · 选项

建设与开通选项

底座必选，政务能力按需叠加。所有租户共享同一套网关与租户模型，差别只在账本口径和是否运行补贴流程。

底座 · 必选

统一调度网关：一个账号、一个 API Key 调用授权模型；智能路由把简单任务分给更合适的模型；企业子账号与基础用量展示。

选项 A · 政务级计量结算 OPTIONAL

把每一次调用变成可复核的财政与企业账单：五维计量、价格版本不可回改、三账户、三方对账、对公开票，日志按政务口径留存。

选项 B · 补贴发放通道 OPTIONAL

把算力或模型使用支持从线下拨付改成「申报—审核—额度到账—调用抵扣—复盘」。依赖选项 A，没有可信计量就不能自动兑付。

三种开通组合

组合 1 · 企业调度版

只开通统一调度网关与企业基础出账。适合种子验证、入驻企业和现有集成客户先用起来。

底座

组合 2 · 治理结算版

网关 + 政务级计量结算。满足国企分摊、对公开票、用量审计，但暂不运行补贴政策。

底座 + 选项 A

组合 3 · 政策兑付版

在计量账本之上开通补贴发放通道，形成政策、申报、抵扣、监管闭环。区县算力补贴场景（例如青浦需求梳理中的兑付形态）走这一档，而不是另做一套系统。

底座 + 选项 A + 选项 B

可叠加：AI 企业化部署服务

与上面三种开通组合正交。无论企业只开调度版，还是已经升级到治理结算或政策兑付，都可以按项目叠加部署服务：把推荐分析落到现有业务系统、专属实例或客户指定的私有化边界。它不改变账本和补贴选项的开关，也不并进 SaaS 订阅费。

选项 A 开通后增加的能力

  • 五维计量：企业 / 部门 / 员工 / API Key / 模型与时段。
  • 输入、输出分开计价，缓存命中单独记账，价格版本不可回改。
  • 三账户并行：现金余额 / 政府补贴额度 / 赠送额度；补贴与现金必须分账、可单独出账和核销。
  • 日账单、月账单；平台计量、上游账单、企业确认三方对账。
  • 对公转账、电子发票；请求级留痕，政务口径日志留存建议 3 年。
  • 异常烧钱告警、敏感词过滤，满足审计抽查；需要时再叠加驾驶舱、等保与国密等配套要求。

选项 B 开通后增加的能力

  • 按企业类型配置额度，例如高新、专精特新、规上、初创等（具体类型以书面政策为准）。
  • 按模型倾斜：国产授权模型可设更高补贴比例，引导信创方向使用。
  • 企业在线提交资质 → 主管部门在线审核 → 额度自动入账。
  • 调用时自动抵扣补贴，现金与补贴分账，余额 / 已用 / 剩余透明。
  • 可限定场景与模型白名单；境外通道即使底座可接，也不进入补贴抵扣。
  • 监管侧可看发放总额、发放对象、使用场景和异常，便于复盘。
选项 B 必须有书面政策、审核权限和资金渠道后才能开通。补贴白名单默认只含国产授权模型。不把尚未确认的机关名称写进对外材料。

收入结构

模型原厂官方 API 与能力在已签约前提下，可能有渠道折扣或承诺消费返点（不作对外主卖点）

企业客户真实调用与预算—
政策资金（仅组合 3）按政策核发的使用额度资金本身不是平台收入；平台只收通道建设、审核流与运维服务费

收入一：平台 / 技术服务费（主）

按实际消耗收取约 8%–15%，或折成年框。对应账单、发票、预算、SLA 与支持。不随上游降价等比例消失，且便于国企审计「买的是服务」。

收入二：集采附带价差（辅）

同一模型多渠道仍可能有价差，但对外采用可审计口径：成本可见或合同内可核对，避免「加价黑盒」。倒挂时自动告警或停售新增开通。

收入三：企业化部署与政务选项（独立）

AI 企业化部署按项目计价：现状评估、系统对接、专属或私有化实例、培训与运维托管。选项 A / B 的账本、审核流、驾驶舱另按实施与年框。须单独核算，避免拖垮 SaaS 交付节奏。

主要成本仍是上游采购、发票税负、对账人力、失败重试产生的无效消耗。技术服务、转售与财政补贴核销的税目和科目不同，必须在合同前与财务确认。

06 · 流程

六条核心流程

A. 企业从入驻到第一次调用

A1 线索行业、预估用量、对接人
→
A2 资质执照、开票、合同主体
→
A3 开通租户、管理员、预算、可用模型
→
A4 入账预付到账或激活授信
→
A5 试跑创建 Key，调试台首呼
→
A6 计量当天可见用量曲线

B. 需求提报 → 推荐分析 → 落地

客户填结构化表单（场景、任务、语言、上下文、日均量、QPS、预算、数据敏感级、部署形态）。系统做硬约束过滤后，输出省钱 / 均衡 / 高质量三套方案，并附对比分析：为什么推荐、相对全走旗舰模型能省多少、迁移改动、合规与单点风险。顾问在一个工作日内补充说明与试用额度。一期不做自由文本 LLM 解析，保证结果可复算、可解释，便于国企评审。

F. 企业化部署（按项目）

F1 评估现状、数据分级、约束
→
F2 方案推荐报告 + 部署蓝图
→
F3 环境网关 / 专属 / 私有化
→
F4 对接业务系统、权限与 SSO
→
F5 验收用例、安全、计量回写
→
F6 运营培训、SLA、月度优化

C. 调用 → 计量 → 结算

鉴权与余额预检 → 按成本与健康度选择授权渠道 → 流式转发并异步计量 → 按请求当时的价格版本入账（request_id 幂等）→ 日结月结 → 平台计量、上游账单、客户确认三方对账，差异超过 0.5% 出核查工单。开通选项 A 后，同一笔调用同时写入现金 / 补贴 / 赠送账户规则。

D. 上游变价时的毛利保护

新价格只产生新版本，历史账单不改。系统重算在售模型毛利率，低于阈值告警，低于零对新增客户停售。调价、切渠道或推荐替代需提前在控制台公告，账单标注价格版本。

→
E2 申报企业提交资质
→
E3 审核主管部门在线审批
→
E4 入账额度进入补贴账户
→

→

07 · 推荐

AI 模型推荐分析

推荐分析的目标，是把售前从「给一张报价单」变成「给一份可复核的分析介绍」。它不是不可复制的算法壁垒，而是一套能讲清楚为何推荐、适用边界、成本和迁移代价的方法。权重由客户选择省钱 / 均衡 / 质量策略；合规、出境和数据分级设下限，不允许为省钱把不可用的模型选进来。

分析介绍必须同时写清四件事：适合该场景的模型类型及理由；相对现状或「全部走旗舰模型」的费用差；迁移是改一个接口地址，还是要重写提示词与工具链；以及质量、供应商单点、限流和价格变动风险。若开通选项 B，还须标明方案是否落在可补贴白名单内，避免企业按补贴预期选了不能抵扣的模型。

分析从哪些维度展开

维度看什么对推荐的影响
场景画像生成、抽取、分类、检索、多模态、工具调用；交互还是批处理决定主模型类型，而不是先看品牌
硬约束数据敏感级、是否必须境内、时延、上下文长度、日调用量、预算、是否需要视觉或函数调用先过滤，再打分；不满足约束的模型直接剔除
能力匹配指令遵循、长文本、推理深度、多模态、稳定性与 SLA解释「这个场景为什么适合这一类模型」
成本结构输入 / 输出单价差异、缓存命中、长上下文溢价给出可核对的月度费用区间，而不是口头说便宜
合规标签备案信息、出境属性、渠道来源、是否可进补贴白名单敏感租户默认只保留境内授权模型
迁移代价协议是否兼容、提示词是否要改、工具格式差异写清是「改一行地址」还是「要做应用改造」
运行风险单供应商、调价、限流、幻觉与评测缺口每套方案附降级模型和切换条件

典型场景的推荐倾向

下表是分析框架里的默认倾向，用于介绍和评审，不是对某一家原厂的独家承诺。具体目录以已签约的授权渠道为准，卡片上标明来源与合规属性。

企业场景推荐倾向分析要点
智能客服 / 工单中等体量通用模型做日常会话，旗舰或推理型模型只处理升级会话首字时延和口径一致性优先；知识要以检索增强，而不是让模型硬记业务手册
公文、纪要、材料起草指令遵循稳定的境内通用模型格式、语气和敏感词比极致推理更重要；默认不出境
知识库问答向量检索 + 重排序 + 生成模型分层效果主要取决于检索质量；大模型只负责组织答案并标注来源
代码与运维辅助代码能力突出的模型，仓库不出指定边界若源码不能出内网，走专属实例或私有化，而不是公网旗舰接口
安防与视觉研判多模态视觉模型，和现有告警 / 录像系统对接图或视频帧与文本告警结合；落地走企业化部署，而不是只开一个 API Key
复杂分析与长报告推理型模型，并由路由把简单子任务分给更便宜的模型避免全部流量打到旗舰模型；分析报告里要给出分流后的费用对比

三套方案怎么写

省钱方案

在满足硬约束的前提下，优先中小体量或高性价比推理模型，并尽可能复用缓存。写明质量可能下降的边界，以及何时应升级到均衡方案。

均衡方案（默认）

主模型覆盖日常质量，降级模型和旗舰模型作为备份与升级路径。适合作为国企试点和多数生产流量的起点。

高质量方案

复杂推理、关键对外材料或高风险研判走更强模型。必须同时给出成本上限，以及「哪些请求其实不必走旗舰」的分流建议。

每一套方案都附：主模型与备选、预估月费（按客户填写的量测算）、迁移步骤、风险，以及与部署形态的匹配（公有调度 / 专属实例 / 私有化）。一期用表单加规则打分，结果可复算；效果回流和月度复评放在二期。

08 · 部署

AI 企业化部署服务

企业要的往往不只是「能调到模型」，而是让客服、公文、知识库、安防或内部系统真正用起来。AI 企业化部署服务把推荐分析的结论落地为可验收的系统能力：评估、对接、专属或私有化、安全治理、培训与运维。它与三种开通组合正交，按项目开通，独立核算，不并进平台服务费；但租户、权限、计量和推荐结论与网关共用，避免两套互不相认的账本。

服务包什么

1. 现状评估与蓝图

摸清现有系统、数据分级、网络边界和采购约束，输出架构蓝图、投资测算，以及与推荐分析一致的模型与部署形态建议。

2. 业务系统对接

现有应用改为接入统一网关（兼容接口，尽量少改代码），补齐提示词、工具编排、审核流和人机协同，让调用发生在真实业务流程里。

3. 知识与检索落地

按需建设企业知识库、文档切片、权限过滤和问答引用来源，避免「只会聊天、答不准内部制度」。

4. 专属与私有化

对数据不能出指定边界的客户，提供 VPC 专属实例、本地或行业云私有化，以及混合模式：敏感推理走本地，一般任务走平台调度。

5. 安全与治理

内网访问、密钥托管、操作审计，并与企业目录、SSO 或 OA 对接；日志回写同一套计量，便于分摊和审计。

6. 培训与托管运营

管理员与业务骨干培训、提示词规范、验收用例、SLA 值守和月度优化。上线不是终点，效果要能复盘。

四种部署形态

形态适用数据与调用边界和平台的关系
公有调度一般业务、可接受授权云上调用经统一网关访问已授权渠道默认形态，开通即可用
专属实例用量稳定、需要资源隔离独立计算资源，租户级隔离仍走同一套账号、权限与账单
本地 / 行业云私有化源码、证件、监控或公文不能出指定网络模型和日志留在客户边界内计量规则与推荐结论对齐，账本可汇总到集团
混合部分敏感、部分通用敏感走本地，其余走网关路由策略写进方案，账单能区分来源

平台上对应的功能，而不只是人肉实施

  • 部署工单：从推荐报告一键生成实施清单，包含环境、权限、模型白名单和验收用例。
  • 环境探活与验收：连通性、首呼、计量回写、失败切换都留下记录，作为交付验收依据。
  • 配置同步：私有化或专属环境的模型目录、价格版本和合规标签与主平台对齐，避免两套口径。
  • 应急策略：在客户书面同意的前提下，本地故障可切换到已授权的云上备份通道，切换过程可审计。
  • 运营回写：上线后的用量、错误率和人工反馈回到推荐分析，为二期月度复评提供数据。
部署服务可以单独签约，不强迫客户先买补贴或政务账本；反之，已经开通选项 A / B 的客户，部署时仍使用同一套三账户与补贴白名单，不另建通道。
09 · 账本

计量与结算

底座账本服务所有组合。选项 A 只是把同一套规则升级到政务可审计口径，而不是换一套计费引擎。

#规则原因
1输入与输出分开计价输出单价通常显著高于输入
2缓存命中单独折扣不区分等于把成本优势送给客户或自己吃亏
3多模态按各自单位计图 / 音 / 视频往往不按 token 计价
4以请求发生时的价格版本为准月中调价不可追溯已发生调用
5上游无 usage 时估算并打标对账时优先核查这类记录
6上游失败不计费，平台重试自行承担不能把平台容灾成本转嫁客户
7同一 request_id 幂等扣费队列重放不得重复扣款
8现金、补贴、赠送分账户记账（选项 A）财政资金与企业自付不能混在一张不可分的账单里

默认预付钱包，签约的中大型国企可开后付授信（30 / 60 天）或年框。账本只追加，调整用反向流水冲正。底座明细至少保留 12 个月；开通选项 A 后按政务口径延长留存（建议 3 年），支持按部门、Key、模型解释每一笔，并标明是否命中补贴。

10 · 技术

技术架构与选型

原则不变：网关和计费自己掌控，管理端快速搭建。能买的不写，能二开的不从零造。若已有文档类 AI 中台或 LiteLLM 一类网关，应复用而不是再铺一套。政务选项复用同一计量内核和明细库，只增加账户科目、审核流与监管查询，不复制第二套网关。

层职责建议
接入HTTPS、WAF、第一道限流云负载均衡 + WAF；api 与 console 域名分离
网关鉴权、转换、路由、流式、取用量MVP 基于 MIT 许可开源网关二开；水平扩展；不在此阻塞写库
业务租户、计费、结算、推荐分析、部署工单；可选三账户与补贴审核模块化单体起步，选项以开关和权限启用
异步用量入库、账单、告警、额度抵扣队列 + 消费者，计量不拖垮首字延迟
数据业务库、明细库、缓存、对象存储PostgreSQL + ClickHouse + Redis + OSS
AGPL 许可的网关用于对外 SaaS 前必须做法务结论。MVP 优先 MIT 许可方案。上游密钥走 KMS，企业 Key 只存哈希。等保、国密、信创作为政务组合的配套要求按项目评估，不写进所有商业租户的默认范围。

12 · 风险

风险与合规

风险应对等级
上游转售未授权逐家签渠道协议；合同写明上游变更时的替代与免责高
被当成灰产中转不用「Token 交易」对外表述；只走授权渠道；可说明渠道来源；禁止号池高
价格倒挂每日重算毛利；阈值告警；合同保留调价权高
补贴与现金混账选项 A 强制三账户；选项 B 未授权不开通；发票税目与财政科目事先写死高
数据出境与生成式服务备案模型打标；敏感租户默认境内；境外模型不进补贴白名单；日志按规定留存中高
发票税目签约前与财务确认技术服务、转售或补贴核销口径中
客户集中度监控 Top 客户收入占比，避免单一项目绑架现金流中

一条不能碰的线：不做号池、不借用他人身份、不拆分非授权境外账号，也不把尚未落地的机关名义写进对外方案。
